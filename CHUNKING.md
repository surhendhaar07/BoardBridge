# BoardBridge Document Chunking

## 1. Why Chunking is Necessary

Large Language Models (LLMs) and vector retrieval models cannot ingest entire multi-megabyte codebases or raw documentation files in a single embedding representation. When querying Zephyr RTOS drivers, devicetree bindings, or Kconfig options, engineers need pinpoint retrieval of relevant definitions rather than generic whole-file dumps.

Document chunking breaks long source files and parsed documentation pages into semantically cohesive, bounded passages. Proper chunking:
1. **Adheres to Embedding Context Windows**: Target embedding models (such as `sentence-transformers/all-MiniLM-L6-v2`) have a strict maximum sequence limit of 256 word-pieces (tokens). Feeding longer passages leads to silent truncation and lost semantic information.
2. **Improves Retrieval Precision**: Dense vector embeddings retain higher semantic fidelity when encoding focused concepts (such as a specific driver initialization function or devicetree node binding) rather than sprawling multi-topic files.
3. **Preserves Cross-Boundary Context**: Applying a sliding overlap prevents technical explanations, macro definitions, and code blocks from being arbitrarily split without context.

---

## 2. Chunking Architecture and Strategy

### Heading-First Splitting
BoardBridge adopts a **heading-first hierarchical splitting** strategy:
1. **Heading Isolation**: Document text is first partitioned by section headings identified during document parsing (such as C function signatures, struct definitions, Kconfig symbols, and devicetree `compatible = "..."` bindings).
2. **Context Retention**: Each chunk retains its enclosing section heading in its `section` metadata field, providing continuous architectural context even when the chunk itself is deeply nested.
3. **Section Continuation**: If subsequent pages of a multi-page document do not define new headings, the active section is automatically inherited across pages.
4. **Boundary Isolation**: Section headings and sliding overlaps are strictly reset when transitioning between different documents, preventing semantic leakage across files.

### Paragraph Packing and Word-Bounded Overlap
Inside each section:
1. Paragraphs (delimited by double newlines or logical code blocks) are packed greedily up to `MAX_CHARS`.
2. Paragraphs exceeding `MAX_CHARS` are subdivided using `_cut()`, which prioritizes sentence boundaries (`. `, `! `, `? `), falls back to the nearest whitespace boundary, and avoids severing words mid-token.
3. When a chunk reaches capacity, the subsequent chunk begins with a 150-character overlap extracted from the tail of the preceding chunk. The overlap is guaranteed to begin on a clean word boundary.

### Table Chunking
Tables extracted during ingestion are decoupled from prose text using `strip_table_text()`. Tables are converted into independent chunks (`kind="table"`):
1. Rows are serialized into readable pipe-delimited format (`Col1 | Col2`).
2. The first row is designated as the table header.
3. If an expansive table exceeds `MAX_CHARS`, subsequent table chunks repeat the header row to ensure downstream vector search retains the column schema for every data row.

## 3. Configuration Constants

```python
MAX_CHARS = 1000
OVERLAP = 150
MIN_CHARS = 25
```

- **`MAX_CHARS = 1000`**: Approximately corresponds to ~250 tokens (using the industry standard heuristic of ~4 characters per token). This strictly aligns with the 256 word-piece maximum context length of `all-MiniLM-L6-v2` without risking silent token truncation.
- **`OVERLAP = 150`**: Repeated character window across consecutive chunks (~35-40 tokens). This ensures that function declarations, conditional blocks, or multi-sentence firmware instructions spanning boundaries maintain sufficient context in both adjoining chunks.
- **`MIN_CHARS = 25`**: Discards short fragments, standalone delimiters, and isolated whitespace to keep the vector database free of uninformative noise.

## 4. Chunk Metadata and Record Schema

Every chunk emitted by `chunk_pages()` is an instance of the `Chunk` dataclass containing eight mandatory fields:

| Field | Type | Description |
|---|---|---|
| `doc_id` | `str` | Normalized, collision-free identifier of the source document |
| `source_file` | `str` | Path to the source file in `data/raw/` |
| `page` | `int` | Physical page number (1-indexed) |
| `section` | `str` | Active section heading or firmware symbol |
| `chunk_index` | `int` | Sequential chunk index within the page (0-indexed) |
| `kind` | `str` | `"text"` for prose and code; `"table"` for tabular data |
| `text` | `str` | Cleaned passage content |
| `content_hash` | `str` | SHA-256 hexadecimal digest of whitespace-normalized text |

### Content Hashing
Content hashes are generated by normalizing all internal whitespace runs to single spaces, stripping leading/trailing whitespace, and computing the SHA-256 digest:
```python
content_hash("GPIO pin\nconfiguration") == content_hash("GPIO pin configuration")
```
This ensures idempotent database ingestion and prevents duplicate chunk insertions during iterative re-indexing.

## 5. Chunk Preview Tool

A dedicated, offline command-line preview utility is available in `tools/preview_chunks.py`. It requires no database connection, embedding models, or network access.

### Running the Tool
```bash
python -m tools.preview_chunks data/parsed --n 5 --seed 9
```

### Options
- `folder`: Directory containing parsed `*.jsonl` files (default: `data/parsed`).
- `--n`: Number of random chunks to display (default: 5).
- `--seed`: Random seed for deterministic, reproducible previewing (default: 9).
